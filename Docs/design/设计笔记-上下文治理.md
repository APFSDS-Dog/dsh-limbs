# DSH 上下文治理插件设计笔记

 目标：用更少上下文达成更好结果；把“及时整治”和“压缩交接复盘”拆成不同时间语义的模块，形成可度量、可追溯、可反哺的闭环。

## 一、核心原则

1. 分时间语义
   - 同步：确定性、无 LLM 成本、当轮生效。
   - 异步：可含 LLM 摘要、有成本、对当轮无效，只减负后续轮次。
2. 先确定性，后摘要
   - 去重、截断、落盘、驱逐可重跑结果优先。
   - LLM 摘要只作为最后手段，处理确定性手段啃不动的稳定事实。
3. 压缩必须可追溯
   - 记录压掉了什么、落盘到哪里、是否可恢复，避免复盘时只能看到结果。
4. 交接按任务边界触发，不按水位触发
   - 任务收尾、阶段结论落定时主动换轨，减少中途换轨的信息损耗。
5. 复盘要闭环
   - 复盘产出直接变成下一次任务的预置整治规则，而不是一次性人工观察。

## 二、模块划分

 模块  时间语义  职责  是否调 LLM 
------------
 及时整治  同步  去重、截断大工具输出、失败提醒、失败路径注入、可逆标记  否 
 压缩  异步分层  确定性压缩优先，LLM 摘要兜底，产出可追溯  部分 
 窗口交接  任务边界触发  主动换轨，结构化摘要，复用复盘事实 schema  是（摘要） 
 复盘  事后  度量、反哺整治规则、沉淀事实表示  可少量 

## 三、关键设计点

### 1. 及时整治：同步护栏
- 减少程序汇报、工具汇报的冗余步骤。
- 工具失败时及时提醒模型“已运行过、失败过，换条路”。
- 对“同一工具同一参数”的重复调用可做确定性拦截改写，比单纯提醒更硬。
- 失败信息不要随意改写历史前缀；建议写入独立“尝试记录区”，整治时作为尾部紧凑消息注入。

### 2. 压缩：异步减负，不作为当轮救火
- 第一层：折叠重复行、截断大输出。
- 第二层：大输出落盘、标记可恢复位置。
- 第三层：驱逐可重跑的工具结果。
- 第四层：LLM 摘要，只处理剩余稳定事实。
- 注意：摘要会改写 messages 前缀，可能导致缓存失效；应尽量推迟，并记录影响。

### 3. 窗口交接：单独模块
- 触发条件：任务边界，而非上下文快满。
- 交接摘要结构化：目标、已确认事实、已排除路径、待办。
- 与复盘共用一套事实表示 schema，避免各写各的。
- 新窗口前缀干净，不依赖旧缓存连续性；适合可控与不可控链路。

### 4. 复盘：度量 + 反哺
- 记录每轮输入 token、缓存命中 token、整治前后差值、压缩节省量、摘要成本。
- 复盘产出：哪些冗余可预置截断规则、哪些失败路径应预置提醒、哪些事实应进入交接 schema。
- 复盘不是一次性观察，要形成“复盘 → 规则 → 下次整治”的闭环。

### 5. 可追溯与度量
- 每次整治压缩留轻量标记：压掉了哪些工具输出、落盘位置、是否可恢复。
- 没有度量就无法判断“及时整治”是真有效还是感觉有效。
- 至少跟踪：输入 token、缓存命中 token、整治前后差值、压缩节省量、缓存命中率变化。

## 四、收益判断（稳定估算）

- 可控链路下，压缩严格限定在“纯冗余”上，输入成本节省可做到 60%–70% 量级。
- 一旦摘要开始改写稳定前缀，有效收益会掉到 40%–50% 甚至更低。
- 不可控链路下，压缩收益可能被缓存差价缓存失效吞没，接近无收益；此时窗口接力比会话内压缩更稳。
- 窗口接力在官方链路同样成立：把“破坏缓存”的时机从“水位满了被迫触发”变成“任务边界主动选择”。

## 五、落地顺序建议

1. 先做同步整治：去重、截断、失败提醒、失败路径注入、可逆标记。
2. 加度量：记录输入 token、缓存命中、整治前后差值。
3. 加确定性压缩层：折叠、落盘、驱逐可重跑结果。
4. 摘要异步化：明确它只减负后续轮次，不作为当轮救火。
5. 窗口交接单独模块：结构化摘要，复用复盘 schema。
6. 复盘闭环：产出预置整治规则，反哺下一次任务。
