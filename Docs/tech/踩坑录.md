# 踩坑录（可复用的教训）

> **坑跟知识走，不跟任务走。** 一条坑只要换个任务还会再踩，就该在这里；
> 只属于某次任务的细节 → 那份 `Docs/devlog/t-*`。
> 每条格式：**现象 → 根因 → 绕法**。只写现象不写根因的，等于没记。

## 插件侧（DSH / WebView2）

### #1 · 「配置」点了没反应

- **现象**：底栏「配置」毫无反应，设置面板不弹。
- **根因**：代码只找 `aria-haspopup="dialog"` 且 `aria-label` 含「设置」的按钮。本构建里那按钮不存在 —— `settings.launcher` 被账号行占了，设置是**账号菜单里的一行**（`aria-label="账号菜单"` + `aria-haspopup="menu"`）。
- **绕法**：两种布局都试；先试 dialog 按钮，找不到就点账号菜单再点「设置」。

### #2 · 面板弹了但停在「账号与余额」

- **现象**：能打开面板，但不是「模型」页。
- **根因**：两个叠加 —— ① 面板刚挂载时导航按钮还没渲染，代码立刻返回且不再重试；② 菜单项文字带快捷键后缀，`label === '设置'` 精确比较命中不了，而放宽成 `startsWith` 又会把**菜单容器**算进去，点了等于点空。
- **绕法**：轮询到导航按钮出现再点；菜单项只匹配可点击元素（`button` / `[role=menuitem]` / `[role=button]` / `a`），且只容忍短快捷键尾巴（`labelIsRow`）。

### #5 · 窗口标题带会话名

- **现象**：按标题 `DeepSeek Harness` 精确匹配找不到窗口。
- **根因**：实际标题是「继续设置面板快捷入口任务 — DeepSeek Harness」。
- **绕法**：改包含匹配。另注：本机 `MainWindowHandle` 返回 **0**，必须 `EnumWindows` 找句柄。

### #7 · 残留 `<style>` 让热重载永远显示旧 CSS

- **现象**：连着三次改配色，看起来「完全没生效」。
- **根因**：注入代码原本是「`#dsh-limbs-styles` 已存在就跳过」。热重载换掉了模块，**但上一轮追加的 `<style>` 还在页面里**，于是新 CSS 一次都没装上。
- **绕法**：先 `remove()` 同 id 旧元素，再**无条件**写入当前 CSS 文本；卸载仍由 `ctx.effect` 的 cleanup 负责。

### #8 · CSS 注释里的反引号把模板字符串截断

- **现象**：整个插件解析失败、界面全无；而 `node --check` 照样 exit 0。
- **根因**：`const CSS = \`` 是大模板字符串，注释里写了个含反引号的路径，直接把字符串提前结束。
- **绕法**：注释里去反引号；并在 `.dev/ui-shell-test.mjs` 加「源码卫生」断言（CSS 体长度 > 2000、体内反引号数 = 0、关键选择器存在）—— 同类问题下次**当场红**。

### #16 · `useSyncExternalStore` 的 getSnapshot 每次返回新对象 → 整页白屏

- **现象**：「Limbs 配置」设置页点进去白屏 / 崩溃；同插件另外四处 `useSyncExternalStore`（模型座位、模块二、复盘面板、项目面板）全好。
- **根因**：store 的 `read()` 每次 `return { settings, status, writable }` —— **每调一次就是一个新对象**。React 判定快照是否变化只看**引用**，于是它认为状态永在变化 → 无限重渲染 → `Maximum update depth exceeded` → 整个 `settings.section` 崩掉。官方那四处拿的是官方 store 的 `getSnapshot`，引用天然稳定，所以不犯病。
- **绕法**：store 里加一层快照缓存，**字段逐个比对**，真变了才换新对象：

  ```js
  let cached = null
  const read = () => {
    // ...算出 settings / status / writable...
    if (cached !== null
      && cached.status === status && cached.writable === writable
      && cached.settings.context === settings.context
      && cached.settings.effort === settings.effort
      && cached.settings.costWarn === settings.costWarn) return cached
    cached = { settings, status, writable }
    return cached
  }
  ```

- **为什么离线测试没抓到（这条比上面那条更值钱）**：`.dev/ui-shell-test.mjs` 里的 React 是**替身**，它的 `useSyncExternalStore` 只 `getSnapshot()` 一次就返回，**没有真实的「引用比对 + 重渲染循环」**。所以测试一直是 `89 passed, 0 failed`，真机是白屏 —— **测试绿不代表界面活着**。
- **补的断言**：不补替身的重渲染循环（那等于自建框架），改为直接观测那条可验证的性质 ——

  ```js
  check('the settings snapshot is referentially stable while nothing changed',
    firstSnapshot === secondSnapshot,
    'read() returned a fresh object on every call — React will re-render forever')
  ```

  修前 89 / 1 红，修后 90 / 0 绿。
- **判据**：**任何喂给 `useSyncExternalStore` 的 `getSnapshot`，数据没变时必须返回同一引用。** 写完一个自建 store，先问自己这一句。

### #17 · 模块七「写后自检」与「存档必须已入库」天然互斥，真写永远过不去

- **现象**：`handoff_commit` 四道闸全过、令牌也扣了，却卡在第 ④ 道（写后自检）；自检报的正是**这次刚写进去的东西**：

  ```text
  ❌ 任务账存档已入库
      └─ 账行 t-20261126-02 的存档 t-20261126-02 未入库（clone 后会消失）
  ```

  随后插件自动撤回（devlog 删掉、账表还原），令牌已 `used: true` 作废。**一次收尾白花一张令牌。**
- **根因**：两处规则各对一半，合起来没有解 ——
  - 模块七的写盘段（`lib/handoff.js` 约 L1440–1458）只做 `writeFile(devlog)` + `writeFile(progress)`，**从不 `git add`**；
  - 而 `check_docs.py` 的「任务账存档已入库」查的是 `git ls-files`，**新写的 devlog 在 `git add` 之前必然不在里面**。

  于是「先写盘再自检」的顺序决定了：自检那一瞬间，新账行的存档**永远**未入库 → 永远红 → 永远撤回。
- **判据**：**写后自检的输入必须包含本次写入本身。** 只要自检里有一条检查依赖 VCS 状态，写盘段就必须先把产物 `git add`（只入暂存区，不提交），否则这道闸是死循环。
- **绕法（2026-11-26 已修，见 `t-20261126-02` 的收尾补记与 `lib/handoff.js` 的 `stageForCheck`）**：
  - 写盘段在 `runProjectCheck` 之前掉 `stageForCheck(root, [devlogPath, progressPath])` —— 只 `git add`，**不提交**；
  - 自检报红 → `rollbackWrite()` 之后再来一步 `unstageAfterRollback()`，把两个路径退出索引。**注意**：仓库还没有首次提交时 `git restore --staged` 必然失败（`fatal: could not resolve 'HEAD'`，实测），要退回 `git rm --cached`；
  - 离线测试必须让副本**真的是 git 仓库**（`git init` + 一次基线提交），否则 `git_tracked_files()` 返回 `None` → 那一项走 `⏭️ 跳过`，**跳过看着和通过一样绿**。
- **这一条最值钱的教训不在死锁本身，而在它藏了多久**：副本没有 `.git` 时，「任务账存档已入库」这一项**从来没真跑过**，191 条断言全绿、真写却必然失败。**跳过 ≠ 通过**；要证明一条检查有效，先证明它真跑起来了 —— 所以修完还加了两条断言：输出里**有**「任务账存档已入库」且**不是** ⏭️，并且是 ✅。
- **权宜（已作废）**：闸修好之前曾用「手动收尾」绕过 —— 那是权宜不是方案，别再走。

## 桌面自动化侧（Windows）

### #3 · 模拟点击落进了 Photoshop（**最贵的一条**）

- **现象**：点完 DSH 界面没反应，截图拍到的是 Photoshop。
- **根因**：`SetForegroundWindow` 在 Windows 上并不总能成功把窗口提到前台；`mouse_event` 是**真实系统级输入**，点到的是当前最上层窗口。DSH 被别的程序挡住时，点击就落进别的程序。
- **绕法**：`tools/chain.ps1` 点击前调 `IsForegroundOf($hwnd)`，不是前台就报错退出（exit 2），绝不盲点。
  > **任何模拟点击脚本都应该带这道闸。**

### #4 · 截图与 UIA 状态对不上

- **现象**：UIA 报按钮在 y=833，截图里却在 y=530。
- **根因**：`PrintWindow` 对 WebView2 只返回可见条带（窗口 1400px 高，图 903px），坐标基准被打乱。
- **绕法**：改用 `GetClientRect` + `ClientToScreen` + `CopyFromScreen`，并在**同一进程内**一次取完几何 / UIA / 截图（`tools/state.ps1`）。

### #6 · `pwsh -File` 的数组参数会被空格拆坏

- **现象**：`-Steps 'a','b c'` 被当成一整串。
- **绕法**：改成单个字符串 + `;;` 分隔。

## 样式与主题

### #9 · 主按钮不能用 `brand-primary` 打底配白字

- **现象**：浅色主题下好看，深色主题下白底白字。
- **根因**：`--dsw-alias-brand-primary` 在**深色主题下是近白色**。
- **绕法**：主按钮别用 `brand-primary` 打底。开关的圆钮永远取与轨道**相反**的那个 token：
  - 关 = `label-primary` 圆钮压在 34% 轨道上
  - 开 = `bg-base` 圆钮压在满强度轨道上

  **两种主题都成立。**

**本机 token 实测值**（从截图像素反解，不是肉眼调；对照 `ui-theme/lib/client.js`）

| token | light | dark |
|---|---|---|
| `--dsw-alias-label-primary` | `#0f1115` | `#f9fafb` |
| `--dsw-alias-bg-base` | `#ffffff` | `#151517` |
| `--dsw-alias-brand-primary` | 亮色系 | **近白** |

> 轨道 `rgb(62,62,63)` 对得上 12% 白叠底；圆钮 `rgb(21,21,23)` 对得上 `bg-base`。

## 工具链（Git · 终端 · 沙箱）

### #12 · `git push` 三连失败，看着像凭证问题，其实是会话权限模式

- **现象**：`git push -u origin main` 连续三种方式全失败，报错各不相同 ——
  1. HTTPS（系统默认 `http.sslBackend=schannel`）：
     `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`
  2. 改 `-c http.sslBackend=openssl`：
     `couldn't create signal pipe, Win32 error 5` + `error: failed to execute prompt script (exit code 66)` + `fatal: could not read Username for 'https://github.com'`
  3. 改用 SSH 远端：
     `ssh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5`

  同一时刻手动 `ssh -T git@github.com` 却回「successfully authenticated」—— **这条成功是假线索。**
- **根因**：会话处于受限文件沙箱（`workspace-write`）时，子进程**不能创建命名管道**。三个角色都依赖它：
  - **Git Credential Manager** 靠 `sh` 拉起 helper —— 第 2 条里的 `prompt script` 就是它；
  - **git 自带的 msys `ssh`**（`usr\bin\ssh.exe`）：未设 `core.sshCommand` 时 git 用它，它也要建管道 —— 第 3 条；
  - **schannel** 取 Windows 证书存储被受限令牌挡下 —— 第 1 条。

  `ssh -T` 之所以成功：PATH 上解析到的是 **Windows 原生 OpenSSH**（`System32\OpenSSH\ssh.exe`），不依赖 msys 管道。**两个 ssh 不是同一个**，别拿它的成功当「网络没问题」的证据。
- **绕法（已实测）**：把会话权限提到 `danger-full-access`，**同一条** `git push -u origin main` 直接通过（`7557350..40ecb25  main -> main`）。命令、远端、密钥全没动，唯一变化就是模式。
- **判据**：见到 `SEC_E_NO_CREDENTIALS` / `couldn't create signal pipe, Win32 error 5` / `failed to execute prompt script` 任意一条，**先查会话权限模式**，别动 token、别重配密钥、别怀疑网络。
- **思路（未验证，别当结论）**：若必须留在受限模式，可让 git 改用系统 OpenSSH ——
  `git config core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"`，绕开 msys 的管道依赖。本机权限已放宽，此路**没实测过**。
- **附**：远端可能提示 `This repository moved. Please use the new location: git@github.com:<Owner>/dsh-limbs.git`（仅大小写不同）；推送照常成功，不用理。

## 插件侧 · 桌面端（2026-11-25 模块八目视新增）

### #13 · 桌面端不经过 Host 渲染 `index.html`，`tapIndex` 是空转

- **现象**：插件在 Host 侧挂了三路由，命令行 `Invoke-WebRequest` 全 200，但桌面窗口里的页面一直显示
  「Host 接口没挂上」，`globalThis.__DSH_LIMBS_HANDOFF__` 是 `undefined`。
- **根因**：DSH Desktop 的页面跑在 `dsh-app://app`，文档由外壳从自己的 dist 取；
  它通过 IPC 调 `dshDesktopBoot.ready()` 拿回 Host `collectIndexInjections()` 收集的
  **结构化注入行**，再由页面侧的 `iG()` 逐行 apply（`kind: 'global'` = `globalThis[name] = value`）。
  官方注释也写着「Electron uses file:// plus IPC instead」—— `webServer.renderIndex()`／
  `tapIndex()` 只在「Host 自己渲染 index」那条路上生效。
- **绕法**：订阅 `webserver/index-inject` 事件，往 `table` 里推一行 `{kind:'global', name, value}`。
  这是官方设计好的接入点，两类载体（Host 渲染 + 桌面 IPC）都能吃到。
- **判据**：页面全局缺席而 Host 路由活着 → 先查 `index-inject`，别去怀疑挂载。

### #14 · 桌面端 Origin 是 `dsh-app://app`，只认同源会把每个请求判成跨站

- **现象**：路由在命令行能通，页面侧全是 403。
- **根因**：外壳 `forwardWebRequest` 转发时保留 `Origin: dsh-app://app`；如果同源校验只比
  「Origin 的 host == 请求 URL 的 host」（请求 URL 是 `http://127.0.0.1:<port>`），必然不等。
- **绕法**：把 `dsh-app://app` 列为**唯一额外可信 origin**（`TRUSTED_APP_ORIGINS`）。
  别的 `dsh-app://*` host 仍拒；`http(s)` 的其它站也仍拒。信任边界没变宽 ——
  能发出这个 Origin 的只有桌面外壳主窗口。

### #15 · 「只改一项」的 PUT 把没提交的项写回默认值

- **现象**：在 UI 里点一下热注入开关，本项目的 `write: true` 被悄悄改成 `false`。
- **根因**：校验函数从 `{...DEFAULT_HANDOFF_CONFIG}` 起算再覆盖提交的键，于是返回的是**全集**；
  落盘时「全集」把用户没提交的项也按默认写进去了。
- **绕法**：校验函数返回**补丁**（只含提交的键），落盘时 `{...当前生效, ...补丁}`。
  并加断言：「只提交 inject 时补丁只含 inject」。

### #10 · 清理临时文件时把 `package.json` 删没了
- **现象**：发布后清理 `.dev/awesome/` 与 `%TEMP%`，`package.json` 从磁盘消失。
- **根因**：**未确证**。清理范围与现象之间没找到确凿链路。
- **绕法**：`git checkout -- package.json` 从首个提交恢复。
- **教训**：**删文件这类动作，事后能恢复 ≠ 当时没风险。** 清理前先 `git status` 快照，或把清理改白名单。

### #11 · 同一插件提交了两个大小写不同的市场条目

- **现象**：`APFSDS-Dog__dsh-limbs.yml` 与 `apfsds-dog__dsh-limbs.yml` 在 GitHub 上是两个文件，市场会读成两条记录，**而 CI 全绿**。
- **绕法**：一个插件永远只用一个文件名，认准已合并的那个（本插件 = 全小写）。提新插件前先 `gh pr list --author "@me" --state all`。
