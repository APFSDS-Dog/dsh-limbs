### 落点判断（为什么这么放）

| 事 | 结论 | 为什么 |
|---|---|---|
| 三段放一个文件还是三个 | **一个文件 `lib/handoff.js`** | `MODULE7` §三要求「不要拆成三个插件/三个模块」；三段共用账行解析与四段 schema，拆开就要么互相 import 要么复制 |
| `assemble` 挂在哪 | `lib/host.js` 的 `apply()` 里调 `mountHandoff()` | 与模块二 bridge 同一个容错口径（try/catch 降级），失败不连累模块一/二/三 |
| 工具注册没进 `inject` | **不进** | `inject = ['tools','commands','sessions']` 已含 `tools`；`agent/pre-step` 是 `ctx.on`，不需要额外服务。改 `inject` 会让插件在缺服务的环境整份不加载，代价大于收益 |
| 消息怎么造 | 自己按形状造（`{id, role:'user', content:[{type:'text',text}], source:{kind:'user'}}`） | 插件装进 profile 后解析不到 `@deepseek-ai/*`（profile 的 `node_modules/@deepseek-ai` 只有 `cosmokit` / `schemastery`）。与 `lib/host.js` 现有「刻意不 import」的口径一致 |
| `form` 段 | **不声明**（省略） | `MessageSourceMap['user']` 只有 `{kind:'user'}`；`ContextFormed` 明写「Omitting `form` stays valid — it is the documented default」。声明 `snapshot` 还要造 `sections`，多一层可能不合法的结构 |

## excluded_paths

| 试过 / 考虑过 | 为什么排除 |
|---|---|
| `ctx.systemPrompt.section()` 做注入 | 已验证：`PromptSection` 是 `{name, order, text}`，**没有 cwd 参数**、注册落在插件 scope 是全局的 → A 项目账会注入 B 项目（§5.1 / §八#5）。这是任务书明令禁止项 |
| 每步都注入（不只在首步） | `agent/pre-step` 是每步钩子；每步注入会让 prompt 前缀持续变化，缓存命中率掉下来 —— 省下的上下文又被缓存差价吃回去（决策记录 §8.2） |
| 靠内容哈希做增量去重 | 决策记录 D0-1 明说令牌的**正位是授权**，去重只是副作用；且官方用的是整条 `UserMessage` 深比较（`sameContextPayload`），不是哈希 |
| 直接 `import { createUserMessage } from '@deepseek-ai/dsh-llm'` | 装进 profile 后解析不到该包。要这个依赖就得把它写进 `peerDependencies` 并在宿主侧保证可解析——本轮按「侵入最小」选自造同形对象 |
| 给 `lookup` / `commit` 加 `client.js` 入口 | `MODULE7` §三红线：模块七**不需要 `client.js`**，纯 Host 半边，不占任何 UI 格子 |
| 改 `.dev/postmortem-test.mjs` 的断言「注册了 1 个工具」为 `=== 3` | 数总数会把自己的模块牵连进别人的测试。改成按名字找 `analyze_conversation_efficiency` —— 更贴合原意（真正守的是「模块三的工具在」），代价最小 |
