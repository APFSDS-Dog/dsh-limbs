## confirmed_facts

### A1 置顶：为什么不在 generateMarkdown 里加

`generateMarkdown()` 现在是「六章一尾注」的线性拼装。在它内部插一条 `lines.push` **就是改生成逻辑**，而且会把章节号游标（`section()` 那个 `sectionCursor`）搅进去。所以置顶放在**渲染层**：

| 位置 | 做什么 |
|---|---|
| `renderTopThree(analysis)` | 从 `analysis.suggestions` 取前 3 条，拼成 `### 最该做的三条` 小节（建议为空时如实说「没有产出建议」，不编三条） |
| `withTopThree(markdown, analysis)` | 把该小节插到正文**第一个 `###` 章行之前**（`##` 标题与元信息仍留在最上面） |
| `reviewConversation()` | `analyzeData` → `generateMarkdown` → `withTopThree`，一行串起来 |

`git diff lib/host.js` 的证据：`generateMarkdown` / `analyzeData` 的函数体**零改动**，diff 里只有注释与调用点。

### 一处刻意的语义选择（要记下来）

项目主写的是「保留最近 20 份**或** 30 天内」。实现成「**且**」—— 理由：按字面「或」，一天里连跑 30 次复盘就留 30 份、100 次就留 100 份，那正是「永久增长」本身；「且」才能同时封住数量与时长两个方向，也同时满足两条验收（超 20 份删最旧 + 30 天）。断言已按这个语义钉死，要改回「或」只需改 `pruneReviewReports` 里的一个 `&&`。

### 这一轮踩出来的两个真坑

| 坑 | 现象 | 根因与修法 |
|---|---|---|
| **测试替身的 `useRef` 不持久** | 切会话的 8 条断言假红（「读了好几次」） | 微型 React 的 `useRef` 每次 render 都返回全新 `{current}`，而真 React 跨渲染持久。给替身补了独立的 `refStore`（按 ref 游标），面板才真的记住「已经为哪个会话读过盘」 |
| **`useEffect` 依赖里塞了「读过一次」的布尔** | 面板重渲染频繁，每次都想打 HTTP | 改成 `loadedFor` ref 记**会话 id**，切会话才重读；同时换会话先清 `report/generatedAt/storageOff`，别把上一个会话的报告留在屏幕上 |

## 事后追记（2026-11-27 15:2x，`t-20261127-03` 收尾）

**上面最后那段判错了。** 原文把「真机不成立」归因于「Host 半侧没重载」，并因此把账行压在 `doing`。这个归因后来被 `t-20261127-02` 证伪：

- 桌面版是主进程 + Host worker（多个同名进程），**而且** Host 半侧走 `dsh-hmr` **进程内热替换** —— `lib/host.js` 改了之后进程启动时间**不会变**。拿「进程启动时间 vs 源码时间」判「没重启」，在桌面版上本来就不是可靠判据。
- 真正的病根是三个桥在 `apply()` 里当场 `ctx.get('webServer')`，`webServer` 要异步 bind 端口才 `Service.init`，那一瞬拿不到 → `return undefined` 静默降级 → `/limbs/*` 六条路由**一条都没注册**。

所以「reviews 目录 0 份」不是落盘逻辑坏了，是**读回接口根本没挂**，`review-store-check.ps1` 自然读到 0 份。修好三桥后，`t-20261127-02` 的收尾当场读到 1 份（写于 10:47:27），`t-20261127-03` 复跑五条全 PASS，本行状态转 `done`。
